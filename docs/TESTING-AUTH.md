# Manual auth test matrix

Automated tests (`npm test`) cover the server-side logic of sign-up, email verification, sign-in, password reset and the Google callbacks against an in-memory fake database and mocked email. They do **not** cover anything that needs a real browser, real Google, or real email delivery. This document lists those cases.

## Setup

- Use a staging or local environment with real `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET`, `RESEND_API_KEY` and `EMAIL_FROM` (a verified Resend sender/domain).
- Have three mailboxes you control: **A** (Gmail, also a Google account), **B** (non-Gmail address such as Outlook/iCloud), **C** (a throwaway inbox for spam-folder checks).
- Start each case from a clean state unless stated: delete the user row for the address under test (Prisma Studio) and clear the browser's cookies for the site.
- In production mode (`NODE_ENV=production`) the code is never logged. In development without `RESEND_API_KEY` (or without `EMAIL_FROM`) the code is printed to the server console as `[email:dev] ... verification code: 123456` (or `password-change code: 123456`); that is fine for logic checks, not for delivery checks.
- **Caution: in development the app sends REAL email through Resend whenever both `RESEND_API_KEY` and `EMAIL_FROM` are set in `.env`** (they are in the maintainer's dev `.env`). That includes sign-up codes, reset links, password-change codes and the welcome email. Only use mailboxes you control, and do not spam real or non-existent addresses: bounces and complaints hurt the sending reputation. A testing agent reported that Resend's sandbox recipient form `delivered+<label>@resend.dev` avoids bounces; that is reported, not verified here, so check Resend's documentation for test addresses first. To test without sending, unset one of the two variables and restart the dev server.
- Check which database your `.env` points at before deleting rows or running `db:*` scripts. On the maintainer's machine it is the dev/staging Supabase project, not local Docker (see [feedback-guide.md](feedback-guide.md) section 5). Test accounts and test feedback rows you create there are real rows: delete them afterwards.
- Rate limits for sign-up/sign-in/verify and for the password-change actions are in memory: restart the server to reset them. The code-issuance caps, code attempt counts and the feedback cap are stored in the database and survive a restart.

Legend: "Expect" lines are pass criteria. Record the browser and date next to each case.

## 5. Devices and themes

Repeat these on every listed surface: sign-up, code step, sign-in, forgot/reset password, Google button, and the `/profile` Settings panel and Feedback form (section 6).

- Chrome desktop, Firefox desktop, Safari desktop.
- iOS Safari and Android Chrome (real devices, or DevTools device mode at minimum). Expect: no horizontal scroll at 320 px width, the numeric keypad opens for the code field, the on-screen keyboard does not hide the submit button, the Google flow returns to the app (not stuck in an in-app browser tab), password managers offer to fill/save.
- Installed PWA (if enabled): Google sign-in opens and returns correctly.
- Light and dark theme (toggle the theme, then reload): all text passes contrast, error messages and the requirement checklist are legible, focus rings are visible, the code input is distinguishable, and there is no flash of the wrong theme on reload.
- Keyboard only: Tab order is logical, Enter submits, focus moves to the code field when the code step appears, errors are announced (screen reader: VoiceOver/NVDA).

## Not automated, and why

- Real Google OAuth consent, cancel and deny, and `email_verified` from a live Google profile.
- Real Resend delivery, spam placement, SPF/DKIM/DMARC, including the emailed password-change code.
- Two real browsers: one device keeping its session while the other is signed out after a password change (section 6.5). The unit tests cover the `passwordUpdatedAt` pieces and the cookie round trip, not two live cookie jars.
- Google sign-in for an account that also has a password (section 6.7).
- Wall-clock behavior over minutes/hours (unit tests fake the clock).
- Rendering, responsiveness, themes, accessibility, password-manager/autofill behavior (no jsdom/Playwright yet).
- Multi-instance behavior of the in-memory rate limiter (only valid for a single server process). This matters more than it used to: the app is deployed on Vercel, whose serverless functions run as multiple, independently-scaled instances with no shared memory, so the in-memory counters do not actually enforce a global limit in production — an attacker can get a fresh limiter per instance. Treat any rate-limiting numbers in this doc as best-effort/local-only until that gap is closed (e.g. with a shared store such as Redis/Upstash). This includes the password-change limiters (5 tries per 15 minutes, 5 code requests per hour, per user). The database-backed limits do hold across instances: code issuance (60 s cooldown, 5 per hour), 5 wrong attempts per code, and 5 feedback messages per hour. Those are check-then-insert, so parallel requests can slip past the issuance and feedback caps; see [feedback-guide.md](feedback-guide.md) section 6.
- The real Auth.js `signIn()` internals (unit tests replace `signIn` with a shim that calls the real credentials `authorize` and mimics Auth.js error mapping).
