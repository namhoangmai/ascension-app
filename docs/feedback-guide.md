Two facts to keep in mind while reading:

- The three migrations described here are applied to the maintainer's **dev/staging Supabase database** and to the local Docker Postgres. **Production may be a different database and has not been touched** by any agent. Step 3.1 shows how to find out.
- Vercel builds the code but never applies migrations (see the README). Migrations are a manual step you run yourself, and they go **before** the code.

## 1. What users see and what gets stored

### What users see

The `/profile` page now holds what used to live on a separate `/settings` page. (`/settings` still exists, but only as a redirect to `/profile`, and there is no "Settings" item in the navigation any more.)

- The hero card has a **Settings** button that opens a panel with:
  - **Email** (read-only).
  - **Username** and **Date of birth** (editable). Username uniqueness is case-insensitive: `Bob` and `bob` are the same name.
  - **Change password**, or **Set a password** for accounts that have none (for example Google-only accounts).
- The **last section** of the page is **Feedback & Recommendations**: a category (Feedback or Recommendation) and a message.

Two ways to change a password:

1. Current password plus the new password.
2. **Email me a code**: a 6-digit code is emailed to the signed-in user's own address (never to an address typed into a form), then the user enters the code plus the new password. Setting a **first** password (Google-only accounts) always requires the emailed code.

After a password change the device that made the change stays signed in and every **other** device is signed out on its next request. (Sessions are JWTs, so this is enforced by comparing `User.passwordUpdatedAt` in the database with the value inside the token.)

### Feedback limits (enforced in the app)

| Rule                   | Value                                                                                  | Where                                 |
| ---------------------- | -------------------------------------------------------------------------------------- | ------------------------------------- |
| Category               | `FEEDBACK` or `RECOMMENDATION`                                                         | `src/features/feedback/validation.ts` |
| Message length         | 10 to 2000 characters, after trimming                                                  | `src/features/feedback/validation.ts` |
| Submissions            | Max 5 per user per rolling hour (counted in the database)                              | `src/features/feedback/server.ts`     |
| Who the row belongs to | Always the signed-in user; the user id comes from the session, never from a form field | `src/features/feedback/server.ts`     |

The database itself only enforces types and the foreign key. The length and rate rules live in the app.

### What is stored: table `"Feedback"`

| Column        | Type                      | Notes                                                                                                    |
| ------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `"id"`        | text, primary key         | cuid generated by Prisma                                                                                 |
| `"userId"`    | text, NOT NULL            | Foreign key to `"User"("id")`, `ON DELETE CASCADE`                                                       |
| `"category"`  | enum `"FeedbackCategory"` | `FEEDBACK` or `RECOMMENDATION`                                                                           |
| `"message"`   | text                      | The message as submitted (trimmed)                                                                       |
| `"status"`    | enum `"FeedbackStatus"`   | `NEW` (default), `REVIEWED`, `ARCHIVED`. Nothing in the app changes this; you do                         |
| `"createdAt"` | timestamp(3), default now | UTC                                                                                                      |
| `"updatedAt"` | timestamp(3), NOT NULL    | Set by the Prisma client on insert. There is no database trigger (see the note after the queries in 2.2) |

Indexes: `("userId", "createdAt")` and `("status", "createdAt")`. Row Level Security is enabled on the table with no policies.

### There is no in-app admin view

The feedback form is **submit-only**. Users cannot see what they sent and there is no admin page. You read the table directly in Supabase (next section). Nothing notifies you when feedback arrives (no email, no alert), so check it periodically.

## 2. Reading feedback in Supabase

Table and column names are **case-sensitive quoted identifiers**. In SQL you must write `"Feedback"`, `"createdAt"`, `"userId"` with the double quotes; `feedback` or `createdat` will not be found.

### 2.1 Table Editor

Supabase dashboard, then **Table Editor**, pick schema `public`, open the table `Feedback`. Sort by `createdAt` descending and filter `status` = `NEW` to see what needs attention. The exact menu layout can change, so treat these names as a pointer and check the Supabase docs if something has moved (unverified here).

The Table Editor shows only the `userId`, not who that is. Use the SQL Editor below when you want the email and username.

### 2.2 SQL Editor: ready-made queries

Supabase dashboard, then **SQL Editor**. All queries below were checked against `prisma/schema.prisma` and the migration SQL, and syntax-checked on a local Postgres 16 (see section 7).

Newest first, with who sent it:

```sql
SELECT
  f."createdAt",
  f."category",
  f."status",
  u."email",
  p."username",
  f."message",
  f."id"
FROM "Feedback" f
JOIN "User" u ON u."id" = f."userId"
LEFT JOIN "UserProfile" p ON p."userId" = f."userId"
ORDER BY f."createdAt" DESC
LIMIT 100;
```

Only what is still new:

```sql
SELECT
  f."createdAt",
  f."category",
  u."email",
  p."username",
  f."message",
  f."id"
FROM "Feedback" f
JOIN "User" u ON u."id" = f."userId"
LEFT JOIN "UserProfile" p ON p."userId" = f."userId"
WHERE f."status" = 'NEW'
ORDER BY f."createdAt" DESC;
```

Counts by category and status:

```sql
SELECT "category", "status", count(*) AS n
FROM "Feedback"
GROUP BY "category", "status"
ORDER BY "category", "status";
```

Mark one item reviewed (use `'ARCHIVED'` to archive). Copy the `id` from the first query:

```sql
UPDATE "Feedback"
SET "status" = 'REVIEWED', "updatedAt" = now()
WHERE "id" = '<feedback id>';
```

Mark everything that is currently new as reviewed (run the "only what is still new" query with the same `WHERE` first, so you know exactly what you are changing):

```sql
UPDATE "Feedback"
SET "status" = 'REVIEWED', "updatedAt" = now()
WHERE "status" = 'NEW';
```

Delete a test row by id:

```sql
DELETE FROM "Feedback" WHERE "id" = '<feedback id>';
```

`"updatedAt"` is set explicitly in the updates because Prisma's `@updatedAt` is applied by the Prisma client, not by the database. A manual update does not bump it by itself. The value is cosmetic (nothing in the app reads it), but keeping it right makes the table trustworthy. `now()` goes through the same timestamp conversion as the column's own `CURRENT_TIMESTAMP` default, so the two stay consistent.

### 2.3 Prisma Studio (`npm run db:studio`)

```bash
npm run db:studio     # runs `prisma studio`, opens http://localhost:5555
```

Prisma Studio connects to whatever `DATABASE_URL` your local `.env` holds. **On the maintainer's machine that is the dev/staging Supabase project, not the local Docker Postgres** (see section 5). So Studio shows dev/staging feedback, never production feedback, unless you deliberately point it at production. Studio can edit and delete rows; be careful.

For production, use the Supabase dashboard (2.1 and 2.2) rather than pointing Studio at production.

### 2.4 Things to know before you use it

- **The dashboard editors connect as the `postgres` role.** That role bypasses Row Level Security and is not affected by the `REVOKE` in migration 3 (which only removes the `anon` and `authenticated` API roles' grants). So the Table Editor and SQL Editor keep working on these tables. This is how Supabase documents the `postgres` role; it is not something the repo can prove (unverified, check Supabase docs).
- **The Table Editor can write.** Editing a cell or deleting a row takes effect immediately and there is no undo. Prefer SQL with a `SELECT` first.
- **Privacy.** The join above puts user emails next to their messages. Treat the output as personal data: do not paste it into public issue trackers or chats, and do not leave exports lying around. Opening the `"User"` table in the Table Editor also shows password hashes, so avoid opening it casually and do not screen-share it.
- **Deleting a user deletes their feedback.** `"Feedback"."userId"` is `ON DELETE CASCADE` (migration 1), so removing a `"User"` row removes all of that user's feedback with it. If you want to keep a message, copy it out first.
- **Nothing purges old rows.** Feedback stays until you delete it.

## 3. Production rollout runbook

Do this once, in this order. Migrations first, code second: the new password-change and feedback actions error without their tables, whereas the old code simply ignores the new tables. So a database that is ahead of the code is safe, and code that is ahead of the database is not.

The three migrations (all additive, applied in this order):

1. `20260930111956_profile_settings_feedback`: creates tables `"PasswordChangeCode"` and `"Feedback"` and the enums `"FeedbackCategory"` and `"FeedbackStatus"`, then runs `ENABLE ROW LEVEL SECURITY` (no policies) on both tables.
2. `20260930112045_username_case_insensitive_unique`: creates the unique index `"UserProfile_username_lower_key"` on `lower(username)`. **It fails if two existing usernames differ only by case.** It is not `CONCURRENTLY`, so it briefly blocks writes to `"UserProfile"` while it builds (reads are not blocked); on a small table that is well under a second.
3. `20260930211216_revoke_public_api_roles_new_tables`: revokes all privileges on the two new tables from the `anon` and `authenticated` roles. It is guarded, so it does nothing on plain Postgres where those roles do not exist.

Environment variables production needs (set them in Vercel, names only, never commit values):

| Variable                       | Why                                                                                                                                                              | If it is missing or wrong                                                                                                                                                    |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_SECRET`                  | Signs session JWTs and keys the HMAC of emailed codes. Keep it **stable**.                                                                                       | The app throws in production when it is unset (`src/lib/auth/config.ts`, `src/lib/auth/code-hash.ts`). Rotating it signs everyone out and invalidates all outstanding codes. |
| `RESEND_API_KEY`, `EMAIL_FROM` | Sending sign-up verification codes, password-reset links, password-change codes and the welcome email. `EMAIL_FROM` must use a sender/domain verified in Resend. | In production sending **fails closed**. A password-change code request shows "We could not send the code. Please try again in a minute."                                     |

### 3.0 Before you start

- The env vars above are set for the **Production** environment in Vercel. Vercel applies env var changes to new deployments only, so add them before the deploy in 3.5.
- You have a restore point for the production database. Backup availability depends on your Supabase plan (dashboard, Database, Backups: unverified, check Supabase docs). The migrations are additive, but a restore point is cheap insurance.
- You have a trusted machine with this repo checked out and `npm install` done. You do not need a `.env` for any step below, and you must not write the production connection string into one.

### 3.1 (a) Is production the same Supabase project as dev/staging?

Your local `.env` points at a dev/staging Supabase project (see section 5). Whether the production app on Vercel uses that same project is **unconfirmed**. Find out before you migrate anything, because it decides whether there is anything to do.

Compare **the host and the user part** of the two connection strings, without pasting them anywhere:

1. Vercel dashboard, your project, **Settings**, **Environment Variables**. Find `DATABASE_URL` for **Production** and reveal its value. Look at the host and the user name only, never the password. Check the **Preview** scope too: if Preview points at production, every preview deployment runs branch code against production data.
2. Open your local `.env` yourself and look at the same two parts of `DATABASE_URL`.

How to read them (commonly true for Supabase, unverified here, check Supabase docs):

- Pooler form: host `aws-0-<region>.pooler.supabase.com`, user `postgres.<project-ref>`. The pooler host is **shared by many projects in a region**, so the same host does not prove the same project. The `<project-ref>` in the user name is what identifies the project.
- Direct form: host `db.<project-ref>.supabase.co`, user `postgres`.

If the project refs match, production and dev/staging are the same database: the migrations are already applied, skip to 3.5. If they differ, production is a separate database that has none of the three migrations: continue.

A second check that needs no secrets: open the **SQL Editor** in each Supabase project and run

```sql
SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY started_at;
```

The project that lists `20260930111956_profile_settings_feedback` (and the two after it) has been migrated. The dev/staging project should. The production project should not yet.

If the Vercel value is marked sensitive and cannot be revealed, use the second check and, if still unsure, treat production as un-migrated: `migrate status` in 3.3 will tell you the truth. Do not use `vercel env pull` for this, because it writes the secrets to a file on disk.

### 3.2 (b) Pre-flight SQL on production

Run these in the **production** project's SQL Editor. Both are read-only.

**Username collisions.** Migration 2 builds a unique index on `lower(username)`. This query **must return zero rows**, otherwise migration 2 aborts:

```sql
SELECT lower(username) AS name_lower, count(*) AS n, array_agg(username) AS variants
FROM "UserProfile" WHERE username IS NOT NULL
GROUP BY lower(username) HAVING count(*) > 1;
```

If it returns rows, each row is a set of usernames that differ only by case (for example `Bob` and `bob`). One user in each pair must be renamed before you migrate. Which one keeps the name is a product decision; contact the users if needed. Re-run the query until it returns zero rows. (Exact duplicates cannot exist because `username` is already `@unique`.)

**Role check.** Confirm the role can bypass Row Level Security:

```sql
SELECT current_user, rolbypassrls FROM pg_roles WHERE rolname = current_user;
```

The SQL Editor runs as `postgres`, so this tells you about that role: expect `postgres` and `true`. What matters is the role inside the **production `DATABASE_URL`** that the app uses. Its user name is `postgres` (direct) or `postgres.<project-ref>` (pooler, which maps to `postgres`). If it is anything else, check that role explicitly, because with Row Level Security enabled and no policies, a role that neither owns the tables nor has `BYPASSRLS` would see **no rows** in `"Feedback"` and `"PasswordChangeCode"`:

```sql
SELECT rolname, rolbypassrls FROM pg_roles WHERE rolname = '<role from DATABASE_URL>';
SELECT tablename, tableowner FROM pg_tables WHERE schemaname = 'public' ORDER BY tablename;
```

**Optional: nothing has been applied by hand.** Both values should be `NULL` before the migration:

```sql
SELECT to_regclass('public."Feedback"') AS feedback,
       to_regclass('public."PasswordChangeCode"') AS password_change_code;
```

### 3.3 (c) `prisma migrate status` against production

Use the production connection string **only in this terminal session**, never in a file, never committed. Use the **direct connection or the session-mode pooler (port 5432)** for migrations, not the transaction-mode pooler (port 6543). This is commonly recommended because Prisma's migration commands use session-level features (such as an advisory lock) that transaction-mode pooling does not support (unverified here, check Supabase docs). It is fine if this differs from the `DATABASE_URL` Vercel uses at runtime.

`prisma.config.ts` reads only `DATABASE_URL`. `dotenv` does not override a variable that is already set, so the value you set here wins over anything in `.env`. The connection string is entered hidden and the snippets print only the user and host so you can confirm you are about to hit production and not dev/staging.

PowerShell (Windows):

```powershell
# Enter the production connection string (input is hidden) and keep it in this session only.
$s = Read-Host "Production DATABASE_URL (direct or session-mode, port 5432)" -AsSecureString
$env:DATABASE_URL = [System.Net.NetworkCredential]::new("", $s).Password

# Show what you are about to hit: user and host:port only, never the password.
"user: " + ($env:DATABASE_URL -replace '^[a-z]+://([^:]+):.*','$1')
"host: " + ($env:DATABASE_URL -replace '^.*@([^/?]+).*','$1')

# Read-only: lists which migrations are applied and which are pending.
npx prisma migrate status
```

bash (Git Bash, macOS, Linux):

```bash
# Enter the production connection string (input is hidden) and keep it in this shell only.
read -rsp "Production DATABASE_URL (direct or session-mode, port 5432): " DATABASE_URL; echo
export DATABASE_URL

# Show what you are about to hit: user and host:port only, never the password.
echo "user: $(echo "$DATABASE_URL" | sed -E 's#^[a-z]+://([^:]+):.*#\1#')"
echo "host: $(echo "$DATABASE_URL" | sed -E 's#^.*@([^/?]+).*#\1#')"

# Read-only: lists which migrations are applied and which are pending.
npx prisma migrate status
```

If the user and host lines print **blank**, stop: the variable is empty, and the Prisma CLI would silently fall back to the `DATABASE_URL` in your `.env`, which is dev/staging. Clear it and start again.

Expected result: **exactly these three migrations are pending**, and nothing else is reported (no failed migration, no drift):

- `20260930111956_profile_settings_feedback`
- `20260930112045_username_case_insensitive_unique`
- `20260930211216_revoke_public_api_roles_new_tables`

Stop and investigate if the list is different: more than three pending (the database is behind in other ways), a failed migration, a drift warning, or "up to date" (then the database is already migrated and you can skip to 3.5). Stay in the same terminal for the next step.

### 3.4 (d) `prisma migrate deploy`

Still in the same terminal session as 3.3, with `DATABASE_URL` still set and the user/host printout still checked:

PowerShell:

```powershell
npx prisma migrate deploy
npx prisma migrate status      # expect: database schema is up to date
Remove-Item Env:DATABASE_URL   # always clear it afterwards
```

bash:

```bash
npx prisma migrate deploy
npx prisma migrate status      # expect: database schema is up to date
unset DATABASE_URL             # always clear it afterwards
```

`npm run db:deploy` runs the same `prisma migrate deploy`. **Never** run `prisma migrate dev` (`npm run db:migrate`) or `prisma migrate reset` against production: `migrate dev` can offer to reset the database and `reset` drops all data.

If migration 2 fails (duplicate usernames that the pre-flight missed, because someone signed up in between), Prisma records it as failed and refuses to continue until you resolve it. The fix is: rename the clashing users, then tell Prisma the failed attempt was rolled back and deploy again. This is the standard Prisma recovery flow; confirm it against the Prisma docs before using it:

```bash
npx prisma migrate resolve --rolled-back 20260930112045_username_case_insensitive_unique
npx prisma migrate deploy
```

Then run the read-only checks again: the pre-flight from 3.2 (it should still return zero rows) and the RLS audit from section 4.

### 3.5 (e) Only now: deploy the code

Migrations are applied and verified. Now push or merge to `main`; Vercel builds and deploys production from there (see the README's Deploy section). CI runs on the same push, but it does not apply migrations and is not a substitute for 3.4. (No agent does this step for you.)

Before you push, run `npm run verify`, `npm test` and `npm run build` locally (or open a pull request first and look at the CI run). Every one of them has to pass: a build that fails on Vercel leaves production on the previous deployment, which is safe, but the new code (and the migrations you just applied) then sit unused.

Expected one-time effects of this rollout:

- **Some Google sessions are signed out once.** The staleness check against `User.passwordUpdatedAt` is new in this release (the code at git `HEAD` never compared it). Google sessions minted before the deploy carry a `null` `passwordUpdatedAt` in their token (the old code only copied string values, and Google sign-in supplies a date), so for users whose database value is non-null the new check sees a mismatch and signs them out. Those users sign in with Google again and stay signed in. Password sessions are not affected, because the old code already stored the timestamp as a string.
- **Sign-up verification codes still in flight must be resent.** The HMAC input for email-verification codes gained an `email-verify:` purpose prefix, so a code issued by the old code does not validate on the new code (its 10-minute lifetime is the window). The user taps **Resend**.

### 3.6 (f) Post-deploy checks

On the production site:

1. Sign in with a password account. You should land in the app, not bounce back to `/sign-in`.
2. Open `/profile`. The page loads, the **Settings** button opens the panel, and the **Feedback & Recommendations** form is the last section.
3. Submit a test feedback (for example "Test message from the rollout check"). In the Supabase **Table Editor**, open `public` then `Feedback` and confirm the row is there with `status` = `NEW`. Then delete that test row (2.2).
4. Change a password with **Email me a code** on a test account you own. Confirm the email arrives (Resend dashboard, Emails, if it does not), the code works, and you stay signed in on that browser. An error such as "We could not send the code" usually means `RESEND_API_KEY` or `EMAIL_FROM` is missing or wrong in Vercel.
5. If you have an account with both a password and a linked Google login, sign in with **Continue with Google** and confirm you are **not** bounced back to `/sign-in` (the regression guard in `docs/TESTING-AUTH.md`, case 6.7).
6. Skim the Vercel function logs for the deployment for new errors (Vercel dashboard, your project, Logs: unverified menu name).

### 3.7 (g) RLS audit

Run the audit in section 4 on **both** dev/staging and production. It is independent of this rollout, and no migration in this repo enables Row Level Security on the older tables, so you have to decide what to lock down.

### 3.8 (h) Rollback notes

- **Rolling back the code in Vercel does not undo migrations.** Promoting an earlier deployment only restores the earlier build (see the README's "Manual deploy and rollback").
- **The migrations are additive, so old code keeps working against the new schema.** Old code never references `"Feedback"` or `"PasswordChangeCode"`, and it ignores them.
- **The `lower(username)` index and old code.** It only makes the database stricter: old code that tries to claim `Bob` while `bob` exists now hits a unique-violation (Prisma `P2002`). At git `HEAD` the profile save already catches `P2002` and returns "That display name is already taken.", so this is a friendly error, not a crash. Re-check this for whatever commit is actually live when you roll back.
- **Codes do not survive a code rollback.** Verification codes issued by the new code (with the `email-verify:` HMAC prefix) will not validate on old code, and vice versa. Within the 10-minute lifetime, affected users tap **Resend**.
- **Prisma has no down migrations.** Undoing the schema is manual and destructive (it drops the feedback data), and you would also have to repair the `_prisma_migrations` bookkeeping. Prefer leaving the additive tables in place.

## 4. RLS audit (Supabase)

Supabase exposes tables in the `public` schema through its REST API (`/rest/v1/<table>`) to the `anon` and `authenticated` roles. A table is only protected from that API if **Row Level Security (RLS) is enabled** with no permissive policy, or if those roles have no privileges on it. This app does not use the Supabase client or REST API (there is no `supabase` import in `src/`), but the API still exists on the project whether or not the app uses it.

Run this read-only query in the Supabase SQL Editor, on **both** dev/staging and production:

```sql
SELECT
  n.nspname                                             AS schema_name,
  c.relname                                             AS table_name,
  c.relrowsecurity                                      AS rls_enabled,
  (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) AS policy_count,
  has_table_privilege('anon', c.oid, 'SELECT')          AS anon_can_select,
  has_table_privilege('authenticated', c.oid, 'SELECT') AS authenticated_can_select
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind IN ('r', 'p')
ORDER BY c.relrowsecurity, c.relname;
```

The sort puts `rls_enabled = false` rows first, so problems are at the top.

### How to read the result

- **Expected:** every row has `rls_enabled = true`. `policy_count = 0` is the ideal: with RLS on and no policies, the public API roles are default-denied.
- **Problem:** any row with `rls_enabled = false` where `anon_can_select` or `authenticated_can_select` is `true`. Anyone holding the project's anon key can read (and possibly write) that table at `/rest/v1/<table>`. The most sensitive ones in this schema are `User` (password hashes), `Account` (OAuth tokens), `Session`, `PasswordResetToken`, `EmailVerificationCode`, `UserProfile`, and, if they were ever left unprotected, `PasswordChangeCode` and `Feedback`.
- **Also review** any table that has RLS enabled but `policy_count > 0`: a permissive policy can reopen access. Read the policy before deciding.
- `_prisma_migrations` also appears in the list. It holds migration names and checksums, not user data, but it is in the same exposure class, so decide about it alongside the rest.

The anon key is not used by this app and not referenced by any code, so the practical exposure is limited to the key leaking or being shared. Supabase's model treats the anon key as public by design, though, which is exactly why RLS is the intended control. Disabling the Data API for the project is another mitigation (unverified, check Supabase docs).

### Why the app itself is not affected

Prisma connects with the `DATABASE_URL` role, which is `postgres` (or `postgres.<project-ref>` through the pooler). That role owns the tables and bypasses RLS, so enabling RLS with no policies, and revoking the API roles' grants, does not change what the app can read or write. The role check in 3.2 confirms this for your `DATABASE_URL`.

### What this repo did and did not do

- Migrations 1 and 3 protect **only the two new tables** (`"PasswordChangeCode"`, `"Feedback"`): RLS enabled with no policies, plus the `REVOKE` for `anon` and `authenticated`.
- **No migration in this repo enables RLS on the older tables.** On a database built only from this repo's migrations (checked on the local Docker Postgres), all 28 older app tables, including `User`, `Account` and `Session`, plus `_prisma_migrations`, report `rls_enabled = false`.
- Whether those older tables are reachable through the REST API on your Supabase projects depends on the default grants Supabase gives new tables (they are commonly granted to `anon` and `authenticated`, unverified here, check Supabase docs). The audit shows the truth.
- **No agent locked down the older tables for you. You need to run this audit on both projects and decide what to protect.** The consistent way to do it is a new Prisma migration (so local, CI, dev/staging and production stay identical), which belongs to the backend role; ask for one rather than typing ad-hoc statements into production. As an emergency measure, protecting a single table looks like this (example only, not run by anyone, try it on dev/staging first):

```sql
ALTER TABLE "User" ENABLE ROW LEVEL SECURITY;
```

## 5. Local development and testing notes

- **Your `.env` may not point where `.env.example` says.** `.env.example` and the README describe the local Docker Postgres on host port **5433** (deliberately not 5432). The maintainer has confirmed that their own `.env` `DATABASE_URL` instead points at the **dev/staging Supabase** project (a pooler host on port 5432). This guide cannot read `.env`, so check yours. Because of that, with the default setup these all act on dev/staging, not on local Docker:
  - `npm run dev` (the app reads `DATABASE_URL` at runtime),
  - `npm run db:migrate` (`prisma migrate dev`; on a remote database it may offer to reset on drift, so never accept a reset),
  - `npm run db:deploy`,
  - `npm run db:studio`.

  To see what a command would hit, print the user and host of your current `DATABASE_URL` the same way as in 3.3, or simply open `.env` and look. Do not use a `.env.local` override: the Prisma CLI loads only `.env` (via `dotenv/config` in `prisma.config.ts`), so an override would apply to Next.js but not to Prisma commands.

- **`DIRECT_URL` is not read by anything.** `.env.example`, the README, `docker-compose.yml` and `.github/workflows/ci.yml` all mention `DIRECT_URL`, but `prisma.config.ts` and `src/lib/db/prisma.ts` read only `DATABASE_URL`, and nothing else in the repo reads `DIRECT_URL`. So one `DATABASE_URL` serves both the Prisma CLI and the running app. It is harmless to leave set; it does nothing.

- **In development the app sends real email through Resend** whenever both `RESEND_API_KEY` and `EMAIL_FROM` are set (they are in the maintainer's dev `.env`). That covers sign-up codes, password-reset links, **password-change codes** and the welcome email. Only when either variable is unset does it fall back to logging the code to the server console (`[email:dev] To: ... | ... | password-change code: 123456`) and pretend delivery succeeded. So:
  - Test with mailboxes you control.
  - Do not spam real or non-existent addresses: bounces and complaints hurt your Resend sending reputation.
  - A testing agent reported that Resend's sandbox recipient form `delivered+<label>@resend.dev` avoids bounces. This was reported, not verified here: check Resend's documentation for test addresses before relying on it.
  - To use the console fallback instead, unset one of the two variables in your dev `.env` and restart `npm run dev`.

- **`npm test` runs Vitest** (`vitest run`, files matching `src/**/*.test.ts`). It is hermetic: no `.env`, no database, an in-memory fake database and mocked email. It covers the server-side logic of sign-up, email verification, sign-in, password reset and change, the emailed-code flow, session staleness, account details, feedback and username matching. It does **not** run the Playwright setup in `tests/`, which is separate and in progress.

- **What the manual matrix covers.** `docs/TESTING-AUTH.md` lists what automated tests cannot check: real Google OAuth, real email delivery, wall-clock timing, multiple browsers, and rendering. Section 6 there covers the Profile page: emailed-code password change, current device stays signed in while another is signed out, setting a first password on a Google-only account, Google sign-in for an account that also has a password, case-insensitive username sign-in, and feedback submission.

- **Before you commit:** `npm run verify` (typecheck, lint, format check), plus `npm test`. CI runs the same and `npm run build`.

## 6. Known limitations

These are known and deliberately deferred. Nothing here blocks the rollout.

- **Issuance caps are check-then-insert.** The caps on password-change codes and email-verification codes (60-second cooldown, 5 per hour) and the feedback cap (5 per hour) read the recent count and then insert, so parallel requests can slip past them. The impact is limited: a signed-in user could spam their own inbox, or the feedback table, for an hour. **Guessing a code is not made easier**: wrong-attempt counting (5 per code) uses an atomic conditional update.
- **The in-memory rate limiter is per serverless instance.** `src/lib/auth/rate-limit.ts` keeps counters in process memory. On Vercel every instance has its own counters and they reset on cold start, so the limiter used by `changePassword`, `changePasswordWithCode` and `requestPasswordChangeCode` (and by sign-in, sign-up, forgot and reset password, and email verification) is best-effort friction, not a global limit. The database-backed limits (code issuance caps, code attempts, feedback cap) do hold across instances, apart from the race in the previous point. A shared store such as Redis or Upstash would be the real fix.
- **Expired and used rows are never purged.** Nothing in `src/` deletes old `"PasswordChangeCode"` rows (or `"EmailVerificationCode"` and `"PasswordResetToken"` rows). They are small and indexed by `"expiresAt"`, but they accumulate.
- **Avatar data URLs can bloat the session cookie (pre-existing).** A profile picture is stored as a `data:` URL (validation allows up to about 7 MB), and credentials sign-in returns `image: user.image`, which Auth.js places in the JWT `picture` claim. A large avatar can therefore make the session cookie too big. The effect on cookie size was not measured for this guide.
- **No in-app feedback view and no notification** (by choice, see section 1).
- **Sessions cannot be revoked on demand.** They are JWTs, so "sign out other devices" works only through the `passwordUpdatedAt` comparison on the next request. The `prisma.session.deleteMany` calls in the password flows are no-ops under JWT sessions.

## 7. What could not be verified

- **No database was changed or queried except the local Docker Postgres.** No agent connected to dev/staging or production from this job. Every SQL statement in this guide was checked by reading `prisma/schema.prisma` and the migration SQL, and then run against the **local** Postgres 16 container: the read queries for real, the `UPDATE`/`DELETE` statements inside a transaction that was rolled back, and the RLS audit inside a rolled-back transaction with temporary `anon` and `authenticated` roles. The local database has no feedback rows, so result formatting of real data was not seen.
- **Supabase and Vercel dashboards.** Menu names, the `postgres` role behavior in the dashboard editors, the default grants Supabase gives new tables, session-mode versus transaction-mode pooler ports (5432 and 6543) and Prisma's advisory lock, backups by plan, revealing or hiding Vercel env var values, and disabling the Data API are all from general knowledge, not from the repo. They are marked "unverified, check Supabase docs" where they appear.
- **Resend.** The `delivered+<label>@resend.dev` test address is a tester's report. Check Resend's docs.
- **Whether production shares a database with dev/staging.** It cannot be determined from the repo. Step 3.1 is how you find out.
- **Prisma output wording.** The exact text of `prisma migrate status` and `deploy` output was not captured against a remote database; the guide describes the expected outcome rather than quoting it.
- **What the currently live commit does.** The rollback notes describe git `HEAD`; the commit actually running in production may be older.
